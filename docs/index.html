Overview

A Spotify terminal UI and scriptable CLI for Linux and Windows. Built on the official Spotify Web API with PKCE, local disk caches, OS media watchers, Headless Soloist WebSockets, and desktop client tuning.

Four capabilities in one binary

sptune is a single Rust binary with an interactive terminal UI, a shell CLI, headless Linux Connect playback via Spotify Soloist, and process tuning for the official Spotify desktop client:

1. Terminal UI (sptune) Full mouse and vim-key navigation, draggable playbar scrubber, resizable/collapsible sidebar, time-synced lyrics, in-playlist instant filtering, and a customizable "For You" hub. → 2. Scriptable CLI (sptune pb|play|list|search) Control transport, volume, shuffle/repeat, likes, device transfers, random playlist playback, and custom-formatted searches from window-manager keybinds or shell scripts. → 3. Headless Soloist (Linux) Spawns and pairs Spotify's official headless Linux Connect player (soloist) with real-time local WebSocket state push, replacing 5s Web API polls while active. → 4. Desktop Client Optimizer Applies lean Chromium flags, child-process suspension, working-set memory trimming, and Linux cgroup v2 memory caps to keep the official Spotify Electron app lightweight while gaming or working. →

Design goals

  • Official Spotify Web API only: Unlike clients that use unofficial protocols or bundle librespot, sptune uses only documented Spotify Web API endpoints with OAuth 2.0 PKCE (no client secret), avoiding account-ban risk.
  • Zero-FPS idle and sub-millisecond rendering: When paused and idle, sptune stops redrawing completely. While playing, the playbar redraws once per second when the visible second changes. Viewport-only table building and direct Frame::buffer_mut() writes render a 2,000-track playlist in ~0.78 ms.
  • Minimal API traffic: 7-day coalesced disk caches (library_cache.json and playlist_cache_v2.json) paint playlists and saved libraries immediately on open, then reconcile changes in the background with snapshot_id and tail probes.
  • Zero-token state updates: Linux MPRIS (zbus), Windows GSMTC (win-gsmtc), and local Soloist WebSockets push track and state changes without spending Web API rate-limit tokens.

Requirements & constraints

Account requirements, supported platforms, active player options, and build dependencies.

Core requirements

ComponentRequirement
Spotify accountSpotify Premium is required. The official Spotify Web API does not allow playback control (play, pause, seek, transfer) on free-tier accounts.
Active playback deviceThe Spotify Web API controls playback remotely and does not stream audio itself. You need one active Spotify Connect device: Soloist (headless Linux), the official Spotify desktop app, spotifyd, the web player, or Spotify on mobile.
Operating systemLinux (full TUI, CLI, MPRIS watcher, Soloist headless child, cgroup v2 memory cap) and Windows 10/11 (full TUI, CLI, GSMTC watcher, Win32 process suspend & working-set trim). macOS is not officially supported (untested, no OS integrations).
Rust toolchainStable Rust (edition 2021) via rustup, plus pkg-config and OpenSSL development headers (libssl-dev) on Linux when building from source.

Feature-specific OS integrations

FeaturePlatformUnderlying Mechanism
OS Media Event WatcherLinux & WindowsLinux: D-Bus org.mpris.MediaPlayer2.spotify via zbus (tokio runtime, zero background threads).
Windows: Global System Media Transport Controls via win-gsmtc. Wakes playbar on external track changes without spending API tokens.
Headless Soloist PlaybackLinux (x86_64 / ARM64 / Raspberry Pi)Spawns soloist with an isolated data directory (~/.config/sptune/soloist) and connects to its local WebSocket (ws.port) via tokio-tungstenite for real-time state push.
Desktop Memory LimitLinux (cgroup v2)Applies memory.high / memory.max limits (default 150 MB when enabled) across Spotify's process tree via /sys/fs/cgroup.
Child Process Suspend & TrimLinux & WindowsSweeps Spotify helper processes every 4s to suspend non-essential renderers/utilities and trim working-set memory while preserving audio playback.

No librespotsptune uses the official Spotify Web API only — no librespot or unofficial internal Spotify partner APIs.

Limitations and constraints

Spotify Premium account required
sptune requires a Spotify Premium account. Spotify's official Web API restricts playback control endpoints (play, pause, seek, transfer, queue) and Soloist access to Premium accounts only — free-tier accounts cannot control playback.
First-time Soloist pairing requires official desktop or mobile app
On the very first run of soloist, open the official Spotify desktop or mobile app on the same LAN, open the Devices menu, and select your Soloist device (default sptune) once. The Spotify web player cannot perform initial LAN discovery. After pairing once, sptune transfers playback to Soloist automatically on startup.

Quickstart & Auth

Build sptune from source and complete the one-time PKCE Spotify authorization.

1. Build & install from source

Switch tabs below for Linux (Debian/Ubuntu, Arch, Fedora) or Windows build commands:

# 1. Install OpenSSL headers, pkg-config, and clipboard support
sudo apt update && sudo apt install -y libssl-dev pkg-config

# 2. Install directly from GitHub (or clone and build with --path .)
cargo install --git https://github.com/proxylat/sptune
# or: git clone https://github.com/proxylat/sptune.git && cd sptune && cargo install --path .

# 3. Launch (first run walks through Soloist & Spotify PKCE auth)
sptune
# Arch Linux
sudo pacman -S --needed base-devel openssl pkgconf

# Fedora
sudo dnf install -y openssl-devel pkgconf-pkg-config

# Build & install
cargo install --git https://github.com/proxylat/sptune
REM Build release binary with MSVC toolchain
cargo install --git https://github.com/proxylat/sptune

REM Launch in Windows Terminal
sptune

2. Connect Spotify (OAuth 2.0 PKCE)

sptune authenticates directly with the official Spotify Web API using OAuth 2.0 PKCE. No Client Secret is ever needed or stored.

StepAction
1. Create a Spotify AppOpen the Spotify Developer Dashboard and click Create app. Any app name and description work.
2. Set Redirect URIIn your app settings, add http://127.0.0.1:8888/callback under Redirect URIs and click Save.
3. Copy Client IDCopy the Client ID from the dashboard (ignore Client Secret, PKCE does not use it).
4. Authorize in browserRun sptune, paste your Client ID and port (default 8888). Your browser opens automatically to grant permissions and redirects back to 127.0.0.1:8888/callback.
~/.config/sptune/client.yml (generated automatically) 
client_id: "your_32_character_spotify_client_id"
port: 8888
# Optional: Spotify Soloist headless API key (or set SOLOIST_API_KEY env var)
soloist_api_key: ""

3. First run & device selection

Once authenticated, sptune opens the main layout. Press d (or click the device name in the playbar) to pick an active Spotify Connect playback device, or press ? (or click ⚙️ in the top-right header) to open the live Settings & Shortcuts overlay.

Troubleshooting

SymptomResolution
Compile error mentioning opensslInstall libssl-dev and pkg-config (Debian/Ubuntu) or openssl-devel (Fedora), then re-run cargo install --path .
"INVALID_CLIENT: Invalid redirect URI"Ensure http://127.0.0.1:8888/callback (exact port and /callback path, using 127.0.0.1 rather than localhost) is saved in your Spotify Developer Dashboard
Browser does not open on WindowsCopy the printed authorization URL and paste it directly into your browser's address bar (do not run it in cmd.exe, which splits on &)
Stale or corrupted library/playlist cacheRun sptune clean-cache from the shell, press the Clear Cache row in the ⚙️ Settings menu, or launch with sptune --no-cache

Soloist (Headless Linux)

Official headless Spotify Connect audio playback on Linux with real-time local WebSocket state streaming.

How Soloist works with sptune

Soloist is Spotify's official headless Connect client for Linux (x86_64 and aarch64 / Raspberry Pi). Unlike unofficial streaming daemons, Soloist is published by Spotify and pairs with a personal Developer API key:

  • Isolated child lifecycle: When soloist.enabled: true, sptune spawns soloist --device-name <name> --api-key <key> using an isolated data directory (~/.config/sptune/soloist) so it never conflicts with a standalone Soloist instance.
  • Automatic playback transfer: After the first render and whenever Soloist logs in over its local WebSocket, sptune automatically dispatches TransferPlaybackToDeviceName and targets Soloist on playback.
  • Optional keep-alive on exit: Toggle Keep Soloist running on exit in the ? Settings menu (soloist.keep_running) so music can keep playing in the background after quitting sptune without spawning duplicate instances on restart.
  • One-time Zeroconf pairing (Linux): On a fresh ~/.config/sptune/soloist directory, ensure mDNS is running (sudo systemctl enable --now avahi-daemon), launch sptune, and select your Soloist device once in the official Spotify desktop or mobile Connect picker on the same LAN. After that one-time pairing, Soloist persists its session and logs in automatically on every future run. Diagnostics are written to ~/.config/sptune/soloist/soloist.log.

Interactive & manual setup

On a fresh Linux install, sptune automatically launches the interactive Soloist setup wizard. You can re-run it at any time with:

Run interactive Soloist wizard 
sptune --setup-soloist
StepDetails
1. Generate your API keyVisit developer.spotify.com/dashboard/soloist (requires Spotify Premium) to generate your personal Soloist API key. Set it via SOLOIST_API_KEY in your environment or soloist_api_key: in ~/.config/sptune/client.yml.

If Soloist is enabled without a key or binary, sptune prints a hint and continues normally.

Local WebSocket state & control stream (soloist_ws.rs)

sptune connects to Soloist's local WebSocket server (discovered via ~/.config/sptune/soloist/ws.port):

  • Zero-poll real-time updates & local commands: Track metadata, playback position, play/pause state, volume, shuffle, and repeat are pushed over the local socket into CurrentPlaybackContext, and interactive playback commands are sent over the same low-latency connection.
  • Automatic fallback: While Soloist is the active device, the 5-second Web API playback poll is suspended (soloist_live = true), saving API quota. If you transfer playback to another device or Soloist exits, sptune seamlessly resumes Web API polling.

Desktop Optimization

Tame the official Spotify desktop Electron app with lean Chromium flags, child-process suspension, working-set memory trimming, and Linux cgroup v2 caps.

Why optimize the desktop client?

If you use the official Spotify desktop client as your local audio output device while gaming or running heavy workloads, its stock Electron/Chromium process tree can consume hundreds of MB of RAM and background GPU/renderer CPU cycles, even when minimized. sptune includes built-in OS controls (src/platform/) to strip the desktop client down to a minimal audio engine.

NoteThe best optimization is still using another active device like a phone or Soloist, which consumes much less than an Electron app running directly on the system you are using.

Lean Chromium startup flags (chromium_flags.rs)

When spotify.auto_launch: true and spotify.use_chromium_flags: true are enabled, sptune launches Spotify with a curated flag preset that disables background networking, GPU compositing overhead, disk caches, and telemetry. You can override the preset by creating ~/.config/sptune/chromium_flags.yml (see chromium_flags.yml.example in the repo root):

  - "--disable-software-rasterizer"
  - "--disable-background-networking"
  - "--disk-cache-size=1"
  - "--media-cache-size=1"

4-second process sweeper & memory caps

Because Spotify spawns helper processes several seconds after startup (and may have been launched outside sptune), a background sweeper thread runs every 4 seconds while the UI is active:

Child Process Suspension (suspend_children)Linux & WindowsSuspends non-audio Chromium child/renderer processes (SIGSTOP / NtSuspendProcess), tracking PIDs in an in-memory registry so each helper is suspended once and resumed cleanly when toggled. The playbar Suspend/Resume Processes pill is hidden by default; enable it from the ⚙️ Settings menu.
Working-Set Trim (trim_working_set)Linux & WindowsReclaims idle resident memory pages from Spotify's process tree (EmptyWorkingSet on Windows, process_madvise / page reclaim on Linux).
cgroup v2 Memory Limit (memory_limit_mb)LinuxPlaces all Spotify PIDs into a dedicated user cgroup with memory_limit_mb (default 150 MB), preventing Electron cache growth.

Architecture & Profiling

Core engineering invariants, click-to-play URI offset resolution, cache design, and the Criterion / Iai-Callgrind benchmark suite.

Event loop & render pipeline invariants

  • Unlocked input wait & batching: start_ui() waits on events.next() before locking Arc<Mutex<App>> so the background Network thread is never starved, then drains all queued events via events.try_next() into a single batch before drawing one frame.
  • Viewport-only table building (tui/tables.rs): draw_song_table filters tracks in a single O(N) pass with a pre-lowercased needle (App::track_matches_needle), calls Utc::now() once per frame, and builds TableItems only for the visible window [offset..offset + viewport].
  • Cassowary-free direct buffer rendering (tui/widgets.rs): draw_table_window writes header and visible row cells directly into Frame::buffer_mut() at fixed column offsets, bypassing ratatui::widgets::Table::render and its kasuari constraint solver. Main layout, header, and sidebar splits use direct integer Rect arithmetic.

Click-to-Play URI offset invariant

Clicking or pressing Enter on a song inside a playlist uses Offset::Uri via IoEvent::StartPlaybackAt(context_uri, track_uri) instead of a numeric index (Offset::Position):

Playlist click-to-play dispatch path 
IoEvent::StartPlaybackAt(context_uri, track_uri)
  ──► Network::start_playback_at()
    ──► spotify.start_context_playback(cid, device, Some(Offset::Uri(track_uri)), None)

Why: Numeric positions computed from track_table_raw_index drifted from Spotify's internal index whenever the local disk cache held stale is_playable: false flags or when the user sorted a playlist client-side (e.g., by Date Added or Title). Resolving by track URI in MyPlaylists, PlaylistSearch, and MadeForYou guarantees the exact displayed track plays every time.

Coalesced caches & Developer Request Log

  • Zero-clone cache reads: LibraryCache::get_typed deserializes directly from borrowed &entry.items (Vec::<T>::deserialize(&entry.items)) without cloning the serde_json::Value tree.
  • Coalesced async playlist writes: PlaylistCache::update caps cached playlists at 20 (evicting oldest fetched_at LRU) and coalesces disk writes onto a background thread so multi-page playlist loads never block the Network runtime.
  • Developer Request Log: Enable Developer View in the ⚙️ Settings menu to open a live 25% right-hand split showing token-bucket rate-limit capacity, cooldowns, and timestamp-grouped Web API requests.

Benchmarks, CI gates & profiling

Pull requests are gated in CI by deterministic iai-callgrind instruction counts (must not regress Ir > 2%), strict clippy with -D warnings, and the unit test suite:

# Formatting check (2-space rustfmt gate)
rustfmt --check benches/*.rs src/lib.rs src/tui/*.rs

# Zero-warning Clippy across lib, bin, tests, and benches
cargo clippy --all-targets -- -D warnings

# Full unit test suite (lib + bin tests)
RUSTFLAGS="-D warnings" cargo test --locked
# Deterministic instruction-count benchmark suite (Iai-Callgrind)
cargo bench --bench iai

# Wall-clock Criterion suites (render, cache, tick, config)
cargo bench --bench render --bench cache --bench tick -- --quick

# Linux perf + speedscope profile harness
scripts/profile.sh bench playlist_remove_item
